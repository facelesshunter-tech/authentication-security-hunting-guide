# 01 — Authentication Attack-Surface Mapping

**Source:** `Testing Approach .txt` Phase 1 (read in full) and `Phases checklist.txt` Phase 1, Parts 0–4 (read in full, lines 1–700). All HTTP examples below are illustrative, using fictional hosts and accounts, exactly as labeled in the source material — never real evidence.

This guide is different in kind from the ones that follow it. It doesn't test a single vulnerability class — it builds the map every other guide depends on. Skipping it, or doing it shallowly, is the single most common reason a hunter misses a finding that was reachable the whole time: a legacy login route that never got the MFA fix, a mobile-only endpoint nobody documented, an admin panel reachable because nobody thought to check whether it enforced the same rules as the main app.

## A. Security objective

A complete, accurate attack-surface map should let you answer, for the target application: every place identity can enter or change state, every state the application's authentication system recognizes, and which component makes each security decision along the way. The objective isn't finding a bug yet — it's making every later test targeted and reproducible instead of guesswork.

## B. Attack surface

Inventory every entry point that applies to the target. Not every application implements every item — mark what doesn't apply and move on.

- Registration
- Login (including separate staff/administrator/organization login flows, if present)
- Logout
- Password change
- Forgot-password and reset flows
- Email and phone verification
- MFA enrollment, verification, removal, replacement
- Backup-code recovery
- Passkey registration and authentication
- OAuth/OIDC login
- SAML SSO
- Account linking and unlinking
- Session management (active sessions, device management, remember-me)
- Reauthentication and step-up flows
- Account deactivation and deletion
- Administrative account-management functions
- Legacy authentication routes
- API authentication endpoints
- Mobile-specific authentication endpoints
- Trusted-device functionality

## C. Threat model

The risk this guide addresses isn't a single exploitable bug — it's **incomplete coverage**. If a legacy login route, an old API version, or a mobile-only endpoint doesn't make it onto the map, every later test (password security, MFA, session handling, authorization) will quietly skip it too, and whatever weakness lives there stays unfound not because it's hard, but because nobody looked. The attacker's advantage here isn't skill, it's persistence in finding what the tester didn't map.

Required attacker capability: none beyond normal application use and authorized reconnaissance. Required victim interaction: none. Precondition: authorized access to the application under test, within the agreed scope.

## D. Black-box testing

Work from the outside in, using only what's externally observable.

**General technique, applied per entry point below:** inspect the public landing page, login/account menus, and any visible navigation; capture the actual HTTP traffic generated by normal use; check official API documentation if published; do not assume the login page is the only authentication surface.

### Entry-point-by-entry-point discovery

**Registration.** Look in the public landing page, login/account menus, invitation flows. Record: URL and method, required fields, whether verification is required, initial account status and role. Investigate by registering a controlled account and checking what state it's created in.

```http
POST /api/register HTTP/1.1
Host: app.example.test
Content-Type: application/json

{
  "email": "tester-a@example.test",
  "password": "[REDACTED]"
}
```

Finding criterion: a confirmed violation of intended policy, e.g. a newly registered, unverified account reaching a function restricted to verified accounts. A `200 OK` alone is not a finding.

**Login.** Locate the normal web login, check for separate staff/organization logins. Record endpoint, method, accepted credential format, success/failure response, session/token behavior, MFA requirements, redirect behavior, account-state restrictions. Authenticate with a controlled account and record the state transition; test the normal authorized failure cases.

**Logout.** Locate the control, capture the request, identify the session cookie or token involved. Investigate by logging in, accessing a protected resource, logging out normally, then sending a **fresh** request to the same resource with the former session and comparing to the anonymous baseline. A cached page remaining visible is not proof the session is still valid — only a fresh request proves that.

**Password change.** Inspect account settings. Determine whether current-password verification is required, whether recent auth/MFA is required, and what happens to existing sessions after a successful change.

**Forgot-password and reset.** Map the complete flow: reset requested → message/code issued → token delivered → token submitted → token validated → password changed → sessions handled → user notified. Inspect token expiration, account binding, purpose binding, single-use enforcement, replay prevention, rate limits, host/redirect handling. Do not claim token theft from a token merely appearing in a URL — demonstrate the actual consequence with controlled accounts.

**Email and phone verification.** Identify registration verification, email/phone-change verification, resend functionality. Record delivery method, lifetime, attempt restrictions, account binding. Using your own accounts, determine whether the application accepts only the correct, current proof for the intended account and purpose.

**MFA enrollment, verification, removal, recovery.** Inspect account security settings. Record when MFA becomes active, how enrollment is confirmed, what proof is required to remove or replace an authenticator, how recovery works, whether backup codes are single-use. Compare available operations before and after completing MFA with a controlled account.

**Passkeys and WebAuthn.** Inspect account security settings for passkey registration/removal and authentication challenges. Record the four endpoints involved (registration initiation/completion, authentication initiation/completion), credential-to-account binding, removal and recovery behavior.

**OAuth and OIDC.** Inspect login options for external identity providers. Record authorization and callback endpoints, configured IdP, client redirect URI, account-linking/unlinking flows, logout behavior, `state` handling, PKCE usage, `nonce` handling, ID-token validation, issuer/audience checks.

**SAML SSO.** Locate SSO login options, the service provider, configured IdP, assertion-consumer endpoint, any SAML logout endpoints. Record issuer, audience, destination/recipient, assertion conditions, timestamp validation, request-response correlation, signature-validation implementation, account-mapping rules.

**Account linking and unlinking.** Inspect connected-account settings. Identify link/unlink endpoints and whether linking requires recent authentication. Determine how the application identifies an external account and whether it associates the intended identity with the correct local account.

**Session management.** Inspect security settings for active sessions, individual-session revocation, global logout, device management, remember-me. Observe session behavior after logout, password changes, MFA changes, and other security events against the application's stated policy.

**Reauthentication and step-up.** Identify sensitive operations (password/email/phone change, MFA removal, passkey registration/removal, API-key creation, payout/banking changes, sensitive exports, account deletion, privilege changes). For each, establish the intended authentication requirement and check whether the backend independently validates it.

**Legacy, API, and mobile routes.** Use only permitted sources: official API documentation, authorized frontend source, authorized mobile-client behavior, route definitions, older API-version documentation, explicitly in-scope administrative/partner interfaces. Record route and API version, auth method, MFA requirements, session/token type, account-state enforcement, revocation behavior, rate limiting, authorization requirements. Compare equivalent operations across supported routes using controlled identities — this is the step most hunters skip, and it's where alternate-route findings live. Do not treat an endpoint as vulnerable merely because it is old, undocumented, or absent from the frontend; treating "unusual" as "vulnerable" without comparison is itself a false-positive risk.

## E. Gray-box testing

Combine the black-box map with whatever additional material is authorized: API documentation, architecture docs, authentication configuration, logs, database schema, environment configuration, partial source code, identity-provider settings. The goal at this stage specifically is to find entry points that black-box testing alone would miss — an internal route exposed through a reverse proxy, a mobile API version with no public documentation, an administrative interface not linked anywhere in the frontend. Don't assume partial source code reveals the whole architecture; a middleware function existing in a repository doesn't prove every relevant route actually uses it.

## F. White-box testing

If source code is available, search for registration/login/logout/reset/MFA/OAuth/SAML handlers, controllers, and route definitions directly, rather than relying only on what's reachable through the UI. For each confirmed entry point, trace: route → authentication middleware → authorization checks → service → data access. This both confirms the black-box map is complete and surfaces routes that exist in code but were never exercised through the frontend — a strong candidate for an alternate-route finding in Guide 12 (Legacy Authentication).

## G. Differential testing

The core differential technique for attack-surface mapping is comparing the same logical operation across every route that can reach it: the primary web login vs. a documented legacy login, the main API vs. an older API version, the web flow vs. the mobile flow. For each pair, compare MFA enforcement, account-state enforcement, session/token handling, rate limiting, and authorization requirements. A difference here is a strong lead, not yet a finding — confirm the alternate route is actually reachable and that the difference violates the intended policy before reporting it.

## H. Exploitation and validation

"Exploitation" in a mapping phase means confirming a discovered entry point is real, not just present in a doc or dead frontend code: send the live request, confirm a genuine response, confirm the resulting state actually changes the way the map predicts. An entry point that returns a 404 or redirects to a maintenance page isn't part of the live attack surface, however interesting it looked in source.

## I. False-positive analysis

Common ones specific to mapping:

- An endpoint exists in source or in a route table but has no live, reachable path to it (dead code, feature-flagged off, decommissioned).
- A frontend route exists with no corresponding backend handler (client-side routing only).
- A documented "legacy" endpoint that is well-known as deprecated and has 410/404 responses in production.
- Confusing a CDN, WAF, or gateway response for the actual application's behavior.

Before adding anything to the map as a live entry point, confirm it with an actual authorized request and a genuine response — not an assumption from naming or documentation alone.

## J. Root cause

When a route is missing from the map, the underlying cause is usually one of: undocumented legacy code never decommissioned, mobile-only endpoints with no public API docs, administrative or partner interfaces deployed but never linked, or multiple API versions maintained in parallel without a single source of truth for what's actually live. None of these are "vulnerabilities" by themselves — they're the conditions that let a real vulnerability hide.

## K. Remediation

This is the one guide in the set where remediation is aimed at the organization's engineering process as much as at a specific code fix: maintain a single authoritative inventory of authentication entry points, deprecate and actually remove unused routes rather than leaving them reachable, and apply consistent authentication/authorization middleware across every route that serves the same logical operation — not just the one most recently touched.

## L. Regression testing

Re-run the attack-surface map after every significant release, not just once at the start of an engagement. New entry points (a new mobile endpoint, a new partner integration) are exactly the kind of change that doesn't show up in a diff of the areas you already tested.

## M. Finding documentation

Attack-surface mapping produces a findings register, not individual vulnerability reports — the register then drives every subsequent test. Record, per entry point:

| Item | What to record |
|---|---|
| Entry point | Route, method, or workflow |
| Purpose | Login, recovery, MFA, SSO, etc. |
| Authentication method | Password, session, token, federation, etc. |
| Required state | Anonymous, MFA pending, fully authenticated, etc. |
| Identity source | Local account, identity provider, service account |
| Sensitive inputs | IDs, tokens, role fields, redirect parameters |
| Expected enforcement | Verification, MFA, ownership, tenant membership |
| Observed behavior | What happened during normal testing |
| Suspected weakness | Specific discrepancy, if one exists |
| Evidence | Sanitized request, response, state change, or code path |
| Confidence | Unconfirmed lead, validated defect, or not applicable |
| Next action | Which authorized test should follow |

## Completion criteria

- [ ] Relevant authentication entry points inventoried
- [ ] Applicable account states documented
- [ ] Important state transitions mapped
- [ ] Identity sources identified
- [ ] Major trust boundaries documented (client, frontend, backend, IdP, session store, database, background workers, storage)
- [ ] Client-controlled values that must be server-verified recorded (user ID, tenant ID, role, account status, auth flags, ownership IDs, redirect parameters)
- [ ] Findings register prepared
- [ ] Out-of-scope or unsupported features explicitly marked, not silently skipped

**This phase is complete when you understand where authentication occurs, how identity moves through the application, and which server-side decision protects each transition — not when you've found a vulnerability.** The map is the deliverable here; the vulnerabilities come from applying Guides 02–17 against it.
